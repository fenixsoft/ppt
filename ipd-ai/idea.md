## 洞察
    Claude：运营一个AI原生工程组织
    https://claude.com/resources/articles/running-an-ai-native-engineering-org

    结论：
    - **AI 放大的是吞吐量，不是判断力​**：代码变得便宜后，真正贵的是：这段代码对不对、要不要合并、谁负责、会不会带来安全风险、是否符合系统长期方向。
    - **旧流程会“安静地失效”​​**：很多团队沿用人工时代流程：层层审批、大需求文档、长周期评审。AI 原生环境下，这些流程反而拖慢价值流动，却没人主动废除。
    - **规划可以变轻，验证必须变重​​**：不用再花几周写超长规格说明；可以用 AI 快速试、快速原型。但测试、验收、可观测性、边界条件、回归风险要比以前更严格。
    - **评审重点改变​​**：以前评审是“这代码谁写的、写得规不规范”；现在更要看“意图是否清楚、上下文是否足够、改动影响面多大、是否值得合并”。
    - **所有权不能模糊​​**：AI 能生成大量 diff，但生产事故不会怪模型，只会怪团队。需要明确：人拥有决策，人拥有结果，AI 拥有执行辅助。
    - **招聘与组织结构要变​​**：AI-native 团队更看重：能定义问题的人、能做权衡的人、能设计系统和验证机制的人，而不是只会增加代码行数的人。
    - **真正的 AI-native 组织特征​​**：不是“每个人都装了 Copilot”，而是：流程、指标、评审、上线、回滚、知识沉淀都围绕“人机协同”重新设计。

## IPD-AI的整体架构设计
    主要关注点：核心不是“怎么用 AI 写更多代码”，而是：当 AI 把写代码、改代码、生成原型的成本大幅降低后，需要有怎样的流程、组织、开发平台与之配套

    分层概览：
    管理面（流程管理，可观测性、可运维性）
    研发知识库（企业私有知识、架构约束）

    人提出问题，人确认结果
    质量门禁：以AI对抗式的形式，保证设计、开发、验证和交付物的质量。
    AI 协作层：组织各角色的Agent，在IPD流程下相互协作，完成研发
    需求Agent、设计Agent、开发Agent、测试Agent、验证Agent、运维Agent、……

    研发工具（研发工具、代码仓、CICD流水线、界面原型、嵌入式调试……
    AI Infra（算力、模型）

## 对现有 IPD 流程的具体改造
    引入SDD：IPD 里靠人传话的文档链，改成靠 SPEC 做机器+人共同消费的“意图契约”。
    Claude Code 式的 SDD 核心是：先有 SPEC.md / PLAN.md / tasks.md，AI 按 spec 实现，再用测试/审查门禁验证。
    IPD 的核心是：Charter → Concept → Plan → Develop → Qualify → Launch，中间有 DCP（商业决策）和 TR（技术评审），PDT 跨职能对商业结果负责。
    SDD 不取代 IPD，而是把 IPD 的“计划/开发/验证”阶段从文档驱动升级为 spec-anchored 驱动。

    IPD 环节	                    改造方向
    Charter/立项	                保留，但决策更快，因为试错成本降低了
    计划阶段（需求分析+系统设计）     合并成 spec 定义，PM+SE 联合产出
    开发阶段	                    拆成"接口定义+AI实现+人工审查"三层
    验证阶段	                    测试前置到 spec 阶段就开始写用例
    发布阶段	                    保留，但频率提高（从季度到双周/周）
    评审点（TR/DCP）	            DCP/IPMT需要保留，TR保留关键门禁（架构评审、安全评审）砍掉形式化评审
    变更管理	                    从"变更控制委员会"变成"spec 版本管理"，改 spec 比改代码成本低
